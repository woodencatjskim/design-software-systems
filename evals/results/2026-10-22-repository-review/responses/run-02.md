No material allocation defect is established by this snapshot. Preserve the database invariant; an architecture replacement is unwarranted.

The contract covers both the public API and enabled partner import and forbids accepted allocations above capacity (service/CONTRACT.md:3). The import is reachable through the supplied nightly schedule (service/schedule.json:1).

The API atomically increments only when the resulting allocation fits capacity, then returns success after leaving the connection transaction context (service/api.py:19-24). The import lacks that conditional predicate (service/jobs.py:21-24), but this is not an overselling defect: the complete supplied schema enforces nonnegative allocation and allocated <= capacity for both writers (service/schema.sql:4-6). For example, after the API allocates the last unit, an import attempts another increment; the database rejects it, the transaction context rolls back, and the import catches IntegrityError and returns False (service/jobs.py:19-28). Concurrent increments likewise cannot commit a row violating that constraint. This shared enforcement disproves the suspected unguarded-writer failure.

Executed isolated probes using the supplied schema and functions on SQLite 3.50.2 confirmed that an oversized import returns False without changing allocation; an API allocation of the final unit succeeds; subsequent API/import allocations and a missing-SKU import return False. A concurrent API/import attempt using separate connections to one temporary database produced one success, one rejection, and allocated=1 at capacity=1. These checks demonstrate local behavior, not production load or operational reliability.

No corrective change is required for the demonstrated capacity guarantee. Optionally, give the import the API's conditional update to handle expected stock shortages without exceptions, retaining the database constraint as the common safeguard. Verify both writer orderings, oversized requests, absent SKUs, and simultaneous last-unit attempts; rejected writes must leave allocation unchanged.

The snapshot documents upstream retention of rejected orders (service/CONTRACT.md:3; service/jobs.py:15,27), but contains no scheduler implementation or upstream acknowledgement path. Before claiming that end-to-end guarantee is verified, inspect how False and raised database errors affect acknowledgement and replay, and demonstrate that rejection leaves the order pending. This is an unresolved integration check, not evidence of lost orders. Connection setup and production contention behavior are also absent; establish those facts before proposing retry or deployment changes.
