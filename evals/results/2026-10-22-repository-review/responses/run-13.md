No material architecture defect against the stated acceptance/durability contract is established. Preserve the current commit-before-acceptance ordering; this snapshot does not justify introducing another recovery system.

The contract requires every accepted message to remain readable after writer-process loss and states that SQLite uses explicit transactions with synchronous=FULL; committed data is recoverable, and the database is the sole recovery source (service/CONTRACT.md:3; service/schema.sql:1).

The complete active path satisfies that ordering: api.submit delegates directly to append through yield from (service/api.py:22). append begins a transaction, inserts the message, commits, and only then yields "accepted" (service/storage.py:20–23). Generator execution suspends at the yield after commit has completed. Neither immediate transmission nor a caller leaving the generator suspended moves acceptance ahead of persistence. If execution fails before commit returns, that invocation cannot reach the acceptance yield. Process loss after commit but before transmission may leave an unacknowledged stored message; that does not violate this one-way guarantee, and retries are explicitly excluded.

Verification performed: in an isolated temporary SQLite database configured as specified, a subprocess advanced submit exactly once, observed "accepted" with connection.in_transaction=False, and remained suspended. After forcibly killing that writer, a fresh connection recovered the expected message. This corroborates the critical boundary without relying on generator exhaustion. It is a local process-loss experiment, not evidence about deployed configuration or disk-loss recovery.

There is a narrower operational question: append has no explicit rollback around insert/commit (service/storage.py:20–22). An insert failure can leave the supplied connection in a transaction. Whether that causes later request failures depends on connection reuse and caller cleanup, which are not specified. No acceptance is emitted by the failed invocation, so this is not evidence of accepted-message loss. Before proposing cleanup, establish connection ownership and whether reuse after failure is required; if it is, add rollback for a transaction owned by append and verify a failed insert followed by a valid request on the same connection.

For regression coverage, retain the stop-at-first-event/process-kill check and inject an insert or commit failure to verify no acceptance event escapes. Production assurance additionally needs confirmation that actual connections honor the documented transaction and synchronous settings. Host/disk loss, delivery, media, and retry guarantees remain outside the review contract (service/CONTRACT.md:3).
