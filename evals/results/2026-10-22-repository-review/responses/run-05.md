Repair the acceptance boundary in the existing storage adapter; the snapshot establishes a durability defect without requiring a new component.

1. Acceptance precedes durable commit. service/CONTRACT.md:3 requires accepted messages to survive writer-process loss and states that every yielded event is transmitted immediately. service/api.py:22 forwards storage events directly. service/storage.py:20 begins an explicit transaction, service/storage.py:21 inserts, and service/storage.py:22 yields "accepted" before service/storage.py:23 commits. Python suspends the generator at that yield: commit requires another iteration. A writer crash after the sender receives acceptance therefore loses the uncommitted message. The database is the only recovery source (service/schema.sql:1), so no alternate recovery path covers this interval.

   An isolated file-backed SQLite probe using isolation_level=None and synchronous=FULL consumed the acceptance event, then terminated the writer with os._exit. Reopening the database returned no rows. Fully consuming another submission and reopening preserved its row. This demonstrates the faulty boundary and provides counterevidence against a general persistence failure.

   Move commit before yielding acceptance. Emit acceptance only after successful commit; propagate commit failures through the existing error path without reporting acceptance. Verify by terminating the writer immediately after the first event and asserting that a fresh connection reads the exact message. Also inject insert/commit failures and assert that no acceptance is emitted.

2. Transaction lifetime is coupled to stream consumption. There is no cleanup around service/storage.py:20–23. Closing the generator while suspended at acceptance skips commit and leaves the transaction active; the isolated probe confirmed connection.in_transaction remained true after stream.close(). If that connection remains open, its write transaction can block other writers; reuse can also fail when beginning another transaction. An insert exception after BEGIN similarly lacks rollback.

   Finish the transaction before yielding and roll back failed operations before propagating the exception, respecting the adapter's transaction ownership. Verify that stream closure and failed inserts leave no active transaction and that a subsequent writer succeeds.

The complete active path and explicit transaction contract establish these defects. The snapshot does not establish production incident frequency, connection-pool behavior, or how long an abandoned connection remains open; inspect connection lifecycle and transport cancellation handling to quantify operational impact. The probes used local SQLite and are not deployment validation. Host/disk loss, retries, and recipient delivery are explicitly excluded (service/CONTRACT.md:3), so replication, deduplication, and delivery infrastructure are not justified repairs here.
