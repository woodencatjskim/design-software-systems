The snapshot does not establish a material implementation defect, but it leaves the acceptance-durability guarantee unresolved. Do not select a storage repair until the deployed adapter’s acknowledgement and recovery behavior are known.

The active endpoint must preserve accepted jobs across worker-process loss (service/CONTRACT.md:3). The endpoint validates its inputs, calls adapter.append synchronously, and returns "accepted" only after that call returns (service/api.py:30–33). This rules out acceptance before the adapter call completes in the shown path. An exception from append also prevents this function from returning acceptance. However, neither the method name nor its return establishes a durable commit: the protocol supplies only a signature and a generic submission description (service/api.py:6–16).

The material conditional risk is premature acknowledgement. If the injected adapter returns after retaining the job only in worker memory, or before persistence reaches a process-loss-safe boundary, the sequence is: append returns; submit returns "accepted"; the worker dies; the job cannot be recovered. That would violate the contract. Conversely, an adapter that returns only after recoverable persistence, with working recovery, could satisfy the contract without endpoint changes. The snapshot contains no evidence to choose between these cases; the private implementation, configuration, and recovery mechanism are explicitly unavailable (service/CONTRACT.md:3). Absence of a local queue or database implementation is not proof of job loss.

Obtain the actual injected adapter and version, deployment configuration, acknowledgement/commit boundary, ownership and lifetime of persisted data, and restart recovery path. Check both storage and recovery: surviving bytes alone do not establish that an accepted job resumes processing. No host-, zone-, or region-loss guarantee is required by the supplied contract.

If acknowledgement precedes recoverable persistence, move it behind that boundary and ensure restart recovery can discover accepted work; avoid unconditional replacement with a new broker. If the existing adapter already satisfies the promise, document that append returns only after process-loss-safe acceptance and verify this contract for supported deployments.

Verification should use the real configured adapter: record accepted job IDs externally, terminate the worker immediately after acceptance and at relevant persistence boundaries, restart, and confirm every accepted job is recoverable. Include persistence failure: no acceptance should be returned when safe admission fails. No such experiment was executed here; a mock adapter could illustrate the conditional failure but could not establish deployed behavior.
