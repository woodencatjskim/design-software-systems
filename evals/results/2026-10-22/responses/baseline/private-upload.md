A presigned URL is a time-limited bearer capability, not automatically single-use. It can generally be reused while valid, subject to the signed operation and storage policy. Issuing an upload URL does not create or publish the file. A successful upload creates an object; application visibility should depend on verified metadata state and authorization, not merely on a key existing.

Keep the bucket private and enforce tenant authorization in the application for both upload and download. Create a durable pending upload record first, tied to the authenticated tenant, user, a random server-selected object key, expected size/type, and expiry. Issue a short-lived presigned upload scoped to that key and operation. Use an upload mechanism that enforces the required size/checksum restrictions. A tenant prefix aids organization but is not a substitute for authorization. Never sign an arbitrary client-provided key.

Upload to a staging location. On completion, verify the upload record, ownership, actual object size/checksum and type as appropriate, and any required scanning. Treat callbacks as retryable and potentially duplicated. Lock or conditionally update the upload row so repeated completion is idempotent and cannot attach an object to a different tenant. Only after validation should a database transaction publish the attachment metadata as ready. Download lookup requires an authorized tenant relationship and ready status, then issues a short-lived GET URL for that exact object.

Prevent a reused upload URL from overwriting published content after validation. One option is to copy the validated staging object into a distinct final key to which no upload URL was issued, then publish that key. With versioning, pin the exact validated version during promotion. An immutable-version reference can also work if every download consistently targets it. Repeated promotion must resolve to the same finalized attachment rather than publish duplicates.

If upload succeeds but metadata publication fails, retain the pending record and retry verification/publication. A final copy can also succeed before the database commit; use deterministic promotion references and reconciliation so retries recover it. Periodically clean expired pending uploads, abandoned staging objects, and unreferenced final objects after a grace period. Cleanup must recheck current publication state and avoid racing an active completion. Object-storage lifecycle rules can clean stale multipart uploads and staging objects, while database-aware reconciliation handles reference consistency.

Presigned download links remain shareable until expiry, so keep their lifetime aligned with access requirements; immediate revocation may require proxying downloads or another controlled access layer.

A CDN is not justified without measurements. Start with regional S3 downloads and measure latency, throughput, geographic distribution, and cost. Add a CDN if those measurements show a benefit, preserving private-origin access and tenant-aware signed delivery.
