## 1. 분석 범위와 읽는 방법

YouTube 원본 페이지의 설명 및 챕터 정보와 **영어 자동 생성 자막 전체 4,621개 구간**을 확인했다. 자막은 약 32,433단어이며 마지막 구간은 03:16:46에 시작한다. 화면에만 등장하는 다이어그램·코드의 세부 사항은 직접 검증하지 않았다. 따라서 이 문서는 영상 화면 전체를 검수한 기록이 아니라 **전체 자막에 기반한 분석과 기술 검증 문서**다.

자동 자막에는 PostgreSQL, Redis, sharding 같은 용어의 인식 오류가 있다. 문맥으로 식별 가능한 용어는 표준 명칭으로 정리했다. 설명란의 챕터 시작 시각과 실제 자막의 주제 전환에는 차이가 있어, 아래 링크는 주로 **관련 내용이 등장하는 자막의 분 단위 시각**을 사용한다. 인용 문장이나 정확한 발화 시작점을 의미하지 않는다.

문서의 구분은 다음과 같다.

|---|---|---|

| **예시** | 문서 작성자가 구성한 양식·시나리오 | 참고 자료; 고정 요구사항으로 사용하지 않음 |

Spotify·Booking.com·WhatsApp은 **유사 서비스를 설계하기 위한 교육용 문제**다. 강의 속 구성, 사용자 수, 보존 기간, 처리량을 해당 기업의 실제 운영 현황으로 간주하지 않는다. 공식 강의 소개에서도 세 서비스를 사례로 사용하는 5단계 설계 프레임워크를 설명한다. [공식 강의 소개](https://www.freecodecamp.org/news/learn-how-to-design-software-systems-like-a-senior-engineer-in-our-new-course/)

## 2. 강의의 핵심 관점

### 2.1 설계 결과보다 의사결정 과정이 중요하다

**강의 요지:** 시스템 설계는 모호한 문제의 범위를 좁히고, 제약에 맞는 선택을 설명하는 작업이다. 요구사항 확인, 데이터/API 설계, 상위 구조, 확장·신뢰성, 트레이드오프 검토의 다섯 단계를 사용한다. 데이터/API와 상위 구조의 순서는 바꿀 수 있다. 면접에서는 소통, 사고의 구조화, 기술적 판단, 실무적 깊이, 시간 관리도 평가한다. [원문 00:05–00:23](https://www.youtube.com/watch?v=soTfFFIQQ8U&t=300s)

**분석:** skill이 재현해야 하는 것은 특정 서비스의 완성된 다이어그램보다 **요구사항 → 설계 선택 → 비용과 실패 조건 → 검증 근거**의 연결이다. 도구 이름이 많아도 이 연결이 없으면 좋은 설계 산출물이 아니다.

| 평가 관점 | skill의 관찰 가능한 행동으로 변환 |
|---|---|
| 소통과 협업 | 확정 사실·가정·미해결 질문을 구분하고, 결과를 바꿀 질문을 우선한다. |
| 구조화 | 범위와 핵심 사용자 흐름을 정한 뒤 각 단계의 결과를 연결한다. |
| 기술적 판단 | 주요 선택의 근거, 대안, 대가, 재검토 조건을 기록한다. |
| 실무적 깊이 | 정상 흐름에 더해 중복·동시성·부분 실패·복구를 설명한다. |
| 시간 관리 | 사용자 목적에 맞게 깊이를 조절하고 핵심 위험을 먼저 다룬다. |

면접에서 단계마다 면접관과 확인하라는 조언을 에이전트의 매 단계 승인 요청으로 옮기지 않는다. 사용자가 이미 제공한 요구사항과 권한 범위 안에서는 진행하고, 중요한 미확정 조건만 질문하는 방식으로 변환한다.

### 2.2 세 사례는 서로 다른 설계 압력을 보여준다

**강의 요지:** 음악 서비스는 오디오와 메타데이터의 분리 및 전송 비용, 예약 서비스는 검색과 예약 확정의 정합성 차이 및 동시 예약, 메신저는 지속 연결과 메시지 전달·기기 동기화·장애 복구를 다룬다. [음악 서비스](https://www.youtube.com/watch?v=soTfFFIQQ8U&t=1435s), [예약 서비스](https://www.youtube.com/watch?v=soTfFFIQQ8U&t=3060s), [메신저](https://www.youtube.com/watch?v=soTfFFIQQ8U&t=6780s)

**분석:** 이를 skill의 세 가지 선택형 심화 경로로 활용할 수 있다.

| 설계 압력 | 대표 질문 | 대표적인 검증 대상 |
|---|---|---|
| 대용량 콘텐츠 전달 | 큰 파일이 애플리케이션 서버를 거치는가? | 대역폭, 원본 부하, 접근 권한, 캐시 정책 |
| 희소 자원 할당 | 두 요청이 같은 마지막 자원을 획득할 수 있는가? | 불변식, 트랜잭션 경계, 멱등성, 보상 |
| 실시간 이벤트 전달 | 성공 응답 뒤 장애가 발생해도 이벤트를 복구할 수 있는가? | 영속성 경계, 재전송, 중복 제거, 순서, 재연결 |

## 3. Skill에 옮길 설계 프레임워크

이 절은 강의의 5단계를 **실행 가능한 절차로 재구성한 보완 지침**이다. 모든 요청에 같은 분량이나 같은 기술 구성을 강제하지 않는다.

### 단계 1. 문제·범위·제약 확정

**수행:** 핵심 사용자, 반드시 성공해야 할 사용자 흐름, 포함·제외 범위를 적는다. 그다음 규모, 지연, 가용성, 정합성, 데이터 보존, 비용 및 운영 제약을 확인한다.

| 확인 대상 | 구체적인 질문 | 산출물 |
|---|---|---|
| 기능 | 핵심 사용자 행동은 무엇이며 무엇을 제외하는가? | 핵심 흐름 및 범위 |
| 규모 | DAU, 피크 동시 접속, 사용자당 행동 수는 얼마인가? | 부하 가정표 |
| 지연 | 어느 연산의 어느 구간을 p95/p99로 측정하는가? | 측정 가능한 목표 |
| 정합성 | 어떤 상태가 틀리면 금전 손실·중복 할당·유실이 생기는가? | 불변식과 일관성 경계 |
| 보존 | 어떤 데이터를 언제까지 누구에게 제공하는가? | 보존·삭제 조건 |
| 현실 제약 | 기존 스택, 팀 규모, 배포 환경, 예산은 무엇인가? | 선택 가능한 설계 범위 |

**검증:** 핵심 흐름이 범위에 포함되는지, 가정이 사실처럼 쓰이지 않았는지 확인한다. “빠른 서비스”처럼 검증 불가능한 요구사항은 수치 또는 관찰 가능한 조건으로 바꾼다.

### 단계 2. 데이터와 외부 계약 설계

**수행:** 핵심 엔터티, 소유자, 읽기·쓰기 패턴, 키·인덱스, 상태 전이를 정한다. 주요 API 또는 이벤트의 요청·응답·오류를 적는다.

보완 지침:

- API의 인증뿐 아니라 리소스 소유권 및 접근 권한을 검증한다.
- 목록 조회에는 페이지 크기, 정렬 기준, 페이지 간 변경의 처리 방식을 정한다.
- 재시도 가능한 쓰기에는 멱등성 키의 범위, 보존 기간, 동일 키·다른 요청의 처리를 정의한다.
- 업무상 불변식은 이를 지키는 트랜잭션·조건부 쓰기·유일성 제약과 연결한다.
- 저장소는 접근 패턴, 트랜잭션 요구, 예상 부하, 운영 역량으로 선택한다.

**검증:** 모든 핵심 사용자 흐름이 계약과 데이터 모델에 연결되는지 확인한다. 엔터티 이름만 있고 조회 방법·동시 변경 방법이 없으면 미완성이다.

### 단계 3. 최소 구조와 데이터 흐름 설계

**수행:** 먼저 요구사항을 만족하는 작은 구조를 제시하고, 대표 읽기·쓰기 흐름을 끝까지 추적한다. 필요하다면 이 단계를 데이터/API 설계보다 먼저 수행한다.

각 구성 요소에는 다음 내용을 적는다.

- 담당 책임과 소유 데이터
- 동기 호출 또는 비동기 이벤트의 입력·출력
- 상태 보유 여부와 수평 확장 조건
- 실패가 다른 구성 요소에 미치는 영향

**검증:** 쓰기 성공의 의미와 권위 있는 원본 저장소가 명확해야 한다. 캐시·검색 색인·원본 데이터가 모두 같은 역할로 표현되면 수정한다.

### 단계 4. 병목·확장·신뢰성 검토

**수행:** 용량 추정과 핵심 불변식을 기준으로 가장 위험한 지점을 고른다. 그 지점에 필요한 확장과 실패 처리를 추가한다.

| 검토 대상 | 확인할 내용 |
|---|---|
| 부하 | 평균·피크, 핫키, fanout, 동시 연결, 외부 서비스 한계 |
| 재시도 | 타임아웃, 최대 시도 수 또는 총 시간, backoff·jitter, 중복 부작용 |
| 캐시 | TTL, 무효화, 미스·장애 시 원본 부하, 오래된 결과의 허용 범위 |
| 비동기 처리 | 영속화, 재처리, 순서, 중복 제거, consumer lag, DLQ 복구 |
| 복제 | 지연, read-after-write, 장애 조치, 허용 데이터 손실 |
| 운영 | 지연·오류·포화도 및 업무상 실패를 감지하는 지표 |

**검증:** “자동 확장”, “재시도”, “복제”라는 단어만으로 문제를 해결했다고 처리하지 않는다. 트리거, 한계, 정상 복귀 조건까지 설명한다.

### 단계 5. 결정·대가·후속 검증 정리

**수행:** 주요 설계 결정을 요구사항과 연결하고, 미해결 위험과 필요한 실험을 정리한다.

| 결정 기록 필드 | 예시 |
|---|---|
| 문제 | 예약 확정 시 재고 초과가 발생하면 안 된다. |
| 선택 | 한 숙박 기간의 재고를 동일 DB 트랜잭션에서 확인·변경한다. |
| 대안 | 조건부 갱신, Serializable 트랜잭션, 행 잠금 |
| 대가 | 인기 재고에 잠금 경합 또는 재시도 비용이 생긴다. |
| 재검토 조건 | 목표 부하에서 잠금 대기 p99가 지연 예산을 초과한다. |
| 검증 | 마지막 객실을 동시에 예약하는 테스트로 재고 불변식을 확인한다. |

**검증:** 기술 선택을 “대규모 서비스에서 자주 사용한다”는 이유만으로 정당화하지 않는다. 구현·배포하지 않았다면 실제 성능이나 복구 성공을 검증했다고 쓰지 않는다.

## 4. 용량 추정: 수치보다 가정과 단위

강의는 설계 전에 트래픽과 저장량을 계산한다. 아래는 **강의의 교육용 입력값을 사용해 직접 재계산한 결과**다. 실제 회사 지표나 벤치마크가 아니다. [음악 추정](https://www.youtube.com/watch?v=soTfFFIQQ8U&t=1500s), [예약 추정](https://www.youtube.com/watch?v=soTfFFIQQ8U&t=3540s), [메시지 추정](https://www.youtube.com/watch?v=soTfFFIQQ8U&t=6960s)

### 4.1 공통 계산식

```text
평균 요청/초 = 일일 활성 사용자 × 사용자당 일일 요청 수 ÷ 86,400
피크 요청/초 = 평균 요청/초 × 피크 계수
일일 논리 데이터 = 일일 생성 레코드 수 × 평균 레코드 크기
물리 저장량 ≈ 논리 데이터 × 보존 기간 × 복제 계수 + 인덱스·버전 등
전송량 = 전송 횟수 × 평균 전송 크기
연결 메모리 ≈ 동시 연결 수 × 연결당 실제 메모리
전달 작업량 ≈ 메시지 수 × 수신자 수 × 수신자당 대상 기기 수
```

초·일·연, bit·byte, MB·MiB를 혼용하지 않는다. 아래 계산은 별도 표시가 없으면 십진수 단위다. fanout·복제·재시도는 사용자 요청 수와 별도로 계산한다.

### 4.2 음악 스트리밍

| 항목 | 입력과 계산 | 결과 |
|---|---|---|
| 오디오 | 3,000만 곡 × 3 MB | 90 TB |
| 곡 메타데이터 | 3,000만 곡 × 100 B | 3 GB |
| 사용자 기본 데이터 | 50만 명 × 1 KB | 0.5 GB |
| 확장 후 오디오 | 2억 곡 × 3 MB | 600 TB |

**분석:** 대형 파일의 저장·전송 경로를 메타데이터 요청과 분리해야 한다는 판단에 유용하다. 다만 곡당 100 B나 사용자당 1 KB는 제목 길이, 색인, 관계 테이블, 플레이리스트 증가분을 포함한 충분한 예산으로 사용할 수 없다.

**추가 계산 예시:** 50만 명 모두 매일 10곡을 곡당 3 MB만큼 받는다고 가정하면 15 TB/일이다. 이는 추가 가정에 따른 전송량이며, 실제 DAU·청취 비율·중도 종료·품질별 비트레이트가 달라지면 값도 바뀐다. CDN 적중률은 원본 부하를 줄이지만 최종 사용자 전송량 자체를 없애지는 않는다.

### 4.3 호텔 예약

| 항목 | 입력과 계산 | 결과 |
|---|---|---|
| 연간 예약 | 연간 11억 room-nights ÷ 예약당 2박 | 5.5억 건/년 |
| 일일 예약 | 5.5억 ÷ 365 | 약 151만 건/일 |
| 평균 예약 처리 | 5.5억 ÷ 365 ÷ 86,400 | 약 17.44건/초 |
| 평균 읽기 | 월 5억 방문 ÷ 30일 ÷ 86,400 × 방문당 5회 읽기 | 약 965 QPS |

**분석:** 예약 건수와 객실 숙박일 수는 다른 단위다. 또한 17.44건/초는 **업무상 예약 요청률**이며, 재고·결제·이력·outbox 등의 실제 DB 쓰기 횟수는 더 많을 수 있다. 평균 부하가 낮더라도 특정 호텔의 마지막 객실에는 경합이 집중된다.

자동 자막의 월간 방문 계산에는 일수 표현의 불일치가 있으므로, 30일이라는 가정을 명시하고 계산했다. 읽기/예약 비율만으로 특정 데이터베이스나 샤딩 필요성을 확정하지 않는다.

### 4.4 실시간 메신저

| 항목 | 입력과 계산 | 결과 |
|---|---|---|
| 일일 메시지 | DAU 5억 × 20개 | 100억 개/일 |
| 평균 생성량 | 100억 ÷ 86,400 | 약 115,741개/초 |
| 피크 생성량 | 평균 × 3~5배 | 약 347,222~578,704개/초 |
| 일일 논리 저장량 | 100억 × 1 KB | 10 TB/일 |
| 1년간 모두 보존 | 10 TB × 365일 | 3.65 PB |
| 30일간 모두 보존 | 10 TB × 30일 | 300 TB |

**분석:** 마지막 두 행은 보존 가정에 따른 상한 성격의 계산이다. 전달 후 삭제, 미전달 메시지 TTL, 사용자별 기록 보존 정책을 정하기 전에는 실제 저장량을 단정할 수 없다. 복제·미디어·인덱스·수신자별 inbox도 별도다.

강의의 동시 연결 5,000만 개와 연결당 10 KB/s를 곱하면 500 GB/s, 즉 약 4 Tb/s다. 산술은 맞지만 **모든 연결이 해당 전송률을 지속한다는 강한 가정**이다. 유휴 연결, 활성 연결, heartbeat, 미디어 경로를 나누어 다시 추정해야 한다.

## 5. 사례별 설계 분석과 재사용 지침

아래 구조·절차는 강의 사례를 바탕으로 작성한 **보완된 설계 예시**다. 실제 기업 내부 아키텍처의 재현이나 강의 도식의 전사가 아니다.

### 5.1 음악 스트리밍: 요청 처리와 파일 전송 분리

관련 원문: [재생·업로드 흐름 00:29–00:35](https://www.youtube.com/watch?v=soTfFFIQQ8U&t=1740s), [데이터·확장 00:40–00:48](https://www.youtube.com/watch?v=soTfFFIQQ8U&t=2400s).

**분석:** 큰 오디오를 처리하는 경로와 사용자·곡·플레이리스트 관계를 처리하는 경로는 부하 특성이 다르다. 이를 분리하면 API 서버 확장과 미디어 전달 확장을 독립적으로 검토할 수 있다.

| 영역 | 설계 예시 | 선택 이유와 비용 |
|---|---|---|
| 메타데이터 | 관계형 DB | 사용자·곡·아티스트·플레이리스트 관계 및 조회 지원 |
| 오디오 원본 | 객체 저장소 | 큰 파일의 수명과 전송을 API 처리에서 분리 |
| 전달 | 직접 다운로드 또는 CDN | CDN은 원본 부하·거리 지연을 줄이나 캐시·접근 통제가 추가됨 |
| 접근 제어 | 인증·권한 확인 후 제한된 URL 발급 | URL 만료와 재발급, 유출 가능성을 관리해야 함 |
| 통계 | 필요 시 비동기 이벤트 | 재생 경로와 통계 처리를 분리하되 이벤트 손실·중복 정책 필요 |

**재생 흐름 예시:** 재생 요청 → 인증 및 콘텐츠 접근 권한 확인 → 메타데이터 조회 → 접근 URL 발급 → 클라이언트가 미디어 경로에서 파일 또는 범위를 수신한다. 사용자 인증과 해당 곡의 재생 권한은 별도 검사다.

**업로드 보완:** 파일 수신과 메타데이터 등록은 서로 다른 저장소에 걸친 작업이다. `pending → ready` 같은 상태를 두고 업로드 완료·형식 검증 이후 공개한다. 한쪽만 성공했을 때 남는 고아 객체나 깨진 참조를 재처리·정리하는 방법을 정한다. 이 상태 설계는 강의의 단순 업로드 흐름을 보완한 예시다.

**Skill에 남길 규칙:** 큰 파일을 API 서버가 중계하도록 설계했다면 그 이유와 대역폭 한계를 설명한다. CDN·객체 저장소·서명 URL을 모든 서비스의 필수 구성으로 만들지는 않는다.

### 5.2 호텔 예약: 검색 결과와 예약 확정 분리

관련 원문: [요구사항·구조 00:53–01:11](https://www.youtube.com/watch?v=soTfFFIQQ8U&t=3180s), [멱등성·재고·동시성 01:17–01:36](https://www.youtube.com/watch?v=soTfFFIQQ8U&t=4620s), [검색 동기화 01:43–01:49](https://www.youtube.com/watch?v=soTfFFIQQ8U&t=6180s).

**분석:** 검색은 최신 상태와 약간 달라도 사용자가 탐색할 수 있지만, 예약 확정은 재고 제약을 반드시 지켜야 한다. 이 차이를 저장소별 일관성 정책으로 명시하는 것이 핵심이다.

권위 있는 재고 단위의 예시는 `(hotel_id, room_type_id, stay_date)`다. 실제 객실 번호 배정과 객실 유형의 예약 가능 수량은 분리할 수 있다.

```text
각 숙박일에 대해:
기존 확정/점유 수량 + 이번 요청 수량 ≤ 허용 재고

숙박일 범위 = [check_in, check_out)
```

체크아웃 날짜에는 숙박 재고를 소비하지 않는다는 가정을 명시한다. 오버부킹을 허용한다면 허용 재고의 정책을 별도로 정의한다. 강의의 10% 같은 수치는 기본값으로 채택하지 않는다. **업무상 허용한 오버부킹**과 **경쟁 상태가 만든 재고 초과**는 다르다.

**서로 다른 두 문제:**

| 상황 | 필요한 보호 | 충분하지 않은 처리 |
|---|---|---|
| 같은 예약 요청 재전송 | 서버의 멱등성 기록과 원자적 유일성 보장 | 제출 버튼 비활성화, UUID 생성만 하기 |
| 다른 사용자의 동시 예약 | 재고 확인·변경을 보호하는 트랜잭션/조건부 쓰기 | 예약 ID를 다르게 발급하기 |

**예약 확정 절차 예시:**

1. 날짜·인원·수량·사용자 권한을 검증한다.
2. 동일한 논리 요청의 멱등성 키를 확인하고, 동일 키를 동시에 처리하지 못하도록 보호한다.
3. 해당 숙박일들의 재고 행을 일정한 순서로 잠그거나 동등한 원자적 조건부 변경을 사용한다.
4. 필요한 모든 날짜의 행이 존재하고 각 날짜의 재고가 충분한지 검증한다.
5. 모든 날짜의 재고 갱신, 예약 상태 기록, 필요 시 이벤트 outbox 기록을 하나의 트랜잭션으로 처리한다.
6. 커밋 후 응답한다. 실패하면 전체를 롤백하고, 재시도 가능한 충돌만 정해진 한도에서 재시도한다.

하나의 날짜가 실패했는데 나머지 날짜의 재고만 차감되는 결과를 허용하면 안 된다. 행 잠금·격리 수준은 실제 DB의 동작을 확인해 선택한다. [PostgreSQL 격리 수준](https://www.postgresql.org/docs/18/transaction-iso.html)

**결제 보완:** 결제 사업자의 처리와 내부 DB 트랜잭션은 하나의 원자적 작업이 아니다. 임시 점유, 만료, 결제 확인, 확정, 취소·환불의 상태를 정의하고 중복·지연된 결제 결과를 처리해야 한다. 결제 타임아웃을 곧바로 결제 실패로 간주하지 않는다. 이 내용은 강의에 등장하는 결제 서비스 구성을 실제 실패 처리까지 확장한 설계 지침이다.

검색 색인·캐시는 후보 탐색에 사용할 수 있지만, 최종 예약은 원본 재고에서 검증한다. DB 기록과 이벤트 발행의 부분 실패를 방지할 필요가 있을 때 outbox 또는 적절한 CDC 경로를 검토한다. outbox 소비자는 중복 이벤트에도 안전해야 한다. [AWS Transactional outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)

**Skill에 남길 규칙:** 희소 자원 할당 문제에서는 먼저 불변식을 쓰고, 그 불변식을 지키는 저장소 연산과 실패 시 롤백 경계를 제시한다.

### 5.3 실시간 메신저: 연결 상태와 메시지 영속성 분리

관련 원문: [구조·프로토콜 01:59–02:09](https://www.youtube.com/watch?v=soTfFFIQQ8U&t=7140s), [다중 기기·오프라인·그룹 02:15–02:28](https://www.youtube.com/watch?v=soTfFFIQQ8U&t=8100s), [비동기 처리·암호화 02:34–02:44](https://www.youtube.com/watch?v=soTfFFIQQ8U&t=9240s), [장애·배포 03:00–03:13](https://www.youtube.com/watch?v=soTfFFIQQ8U&t=10800s).

**분석:** 연결 중인 사용자 위치는 빠르게 바뀌는 운영 상태이고, 수락한 메시지는 복구 가능한 업무 데이터다. 둘을 같은 캐시의 생존 여부에 의존하게 만들면 연결 장애가 데이터 유실로 바뀐다.

| 영역 | 책임 | 주요 실패 조건 |
|---|---|---|
| 연결 서버 | 실시간 송수신, 기기 세션 관리 | 프로세스 종료, 재연결 폭주 |
| 연결 레지스트리 | 사용자·기기와 연결 서버 매핑 | 만료 지연, 오래된 라우팅 |
| 내구성 있는 로그/저장소 | 수락한 메시지 보존 및 재처리 | 쓰기 실패, 복제 장애, 보존 만료 |
| 전달 처리 | 온라인 전달, 오프라인 backlog, 재전송 | 중복, 순서 역전, 일부 수신자 실패 |
| 미디어 경로 | 파일 업로드·다운로드 | 업로드 미완료, URL 만료 |
| push 알림 | 오프라인 사용자의 앱 복귀 유도 | 알림 지연·유실; 메시지 전달과 동일하지 않음 |

#### 메시지 상태 계약

다음은 보완된 예시이며, 제품이 제공하는 표시 이름과 별도로 실제 보장을 정의한다.

| 상태 | 의미 | 성공을 판단할 근거 |
|---|---|---|
| `pending` | 클라이언트가 전송을 시도 중 | 클라이언트 로컬 기록 |
| `accepted` | 서버가 복구 가능한 경로에 메시지를 수락 | 정의된 내구성 조건의 저장/로그 성공 |
| `delivered` | 대상 기기가 수신을 확인 | 수신 기기의 ACK |
| `read` | 사용자의 읽음 동작을 확인 | 읽음 이벤트 및 제품 정책 |
| `failed/expired` | 수락 실패 또는 계약상 보존 만료 | 오류·만료 이유와 재시도 가능 여부 |

**온라인·오프라인 공통 흐름:** 안정적인 메시지 ID 부여 → 인증·권한·크기 검증 → 내구성 조건을 만족하는 기록 → 수락 응답 → 수신자 기기 조회 → 전달 또는 오프라인 대기 → ACK 처리 → 미확인 대상에 대한 재전송·재동기화.

이 순서는 강의 일부의 “먼저 성공 ACK, 이후 비동기 저장” 설명을 보완한다. 낮은 지연 때문에 DB 기록을 비동기로 하더라도, ACK 이전에 내구성 있는 로그가 확보되었는지 명시해야 한다. Kafka를 사용한다면 복제와 producer ACK 설정을 함께 검토한다. [Kafka producer 설정](https://kafka.apache.org/28/configuration/producer-configs/)

#### 다중 기기·그룹·순서

- 메시지 본문, 수신자별 전달 상태, 기기별 동기화 위치를 구분한다.
- 읽음 상태를 사용자 단위로 합칠지, 전달 완료를 어느 기기까지 요구할지 제품 계약으로 정한다.
- 중복 수신은 안정적인 ID로 제거하고, 같은 텍스트를 다시 보낸 정상 메시지를 지우지 않는다.
- 대화별 순서가 필요하면 순서 번호와 누락 구간 복구 방식을 정의한다. 전역 순서는 별도 요구가 없으면 강제하지 않는다.
- 그룹에서는 메시지 본문을 한 번 저장해도 inbox, 전달 상태, push, 기기별 전송 작업은 증가한다.
- 기기의 오래된 상태가 늦게 도착해 `read`를 `delivered`로 되돌리지 않도록 상태 병합 규칙을 정한다.
- 보존 기간이 지난 기기의 재접속은 일반 동기화와 구분하고, 복구 가능한 범위를 사용자 계약에 반영한다.

**샤딩 보완:** 사용자별, 대화별, 메시지별 키는 서로 다른 읽기 비용과 핫스팟을 만든다. 기기 동기화·시간 범위 조회·대규모 그룹의 접근 패턴에 맞춰 파티션 키와 시간 버킷 등을 평가한다. 특정 키 하나를 모든 메신저의 정답으로 정하지 않는다.

**운영 보완:** 전달 지연, 영속화 실패, backlog의 가장 오래된 메시지 나이, 재연결률, 중복률을 관찰한다. feature flag는 클라이언트 호환성, 점진적 활성화, 되돌림 조건과 연결한다. 무작정 재연결하거나 무한 재시도하면 장애 복구 시 부하가 집중될 수 있다.

## 6. 그대로 Skill 규칙으로 만들면 안 되는 설명

강의는 설계 사고를 익히는 자료로 유용하지만, 아래 설명은 공식 문서 또는 강의 내부 요구사항과 대조해 보완해야 한다. 자동 자막 해석의 한계를 고려해 직인용 대신 관련 시각과 요지를 제시한다.

### C1. PostgreSQL 처리량과 샤딩의 필요성

**원문 위치:** [01:07](https://www.youtube.com/watch?v=soTfFFIQQ8U&t=4020s), [01:37](https://www.youtube.com/watch?v=soTfFFIQQ8U&t=5820s).

**분석:** 약 1,000 QPS라는 숫자만으로 PostgreSQL의 한계나 샤딩 필요성을 결론 낼 수 없다. 레코드 수·쿼리 복잡도·인덱스·하드웨어·동시성 조건이 빠져 있기 때문이다.

**보완 지침:** 실행 계획과 부하 측정을 먼저 확인하고, 검색 기능·데이터 크기·핫스팟·운영 비용에 근거해 검색 엔진이나 샤딩을 검토한다. “1,000 QPS이면 16개 샤드” 같은 규칙은 만들지 않는다.

### C2. SQL 검색과 일반 인덱스에 대한 과도한 단순화

**원문 위치:** [00:43–00:44](https://www.youtube.com/watch?v=soTfFFIQQ8U&t=2580s), [01:44–01:45](https://www.youtube.com/watch?v=soTfFFIQQ8U&t=6240s).

일반 인덱스가 자동으로 오타 교정을 제공하지는 않는다. 반대로 SQL의 `LIKE`가 항상 전체 테이블 스캔이라는 설명도 일반화할 수 없다. PostgreSQL의 `pg_trgm`은 유사 문자열 검색과 `LIKE`/`ILIKE`용 인덱스를 지원한다. **검색 요구와 실행 계획을 비교한 뒤 별도 검색 엔진 도입 여부를 결정한다.** [PostgreSQL pg_trgm](https://www.postgresql.org/docs/17/pgtrgm.html)

### C3. Serializable은 모든 트랜잭션을 한 줄로 실행한다는 설명

**원문 위치:** [01:35–01:36](https://www.youtube.com/watch?v=soTfFFIQQ8U&t=5700s).

PostgreSQL의 Serializable은 동시 실행을 허용하면서 직렬 실행과 동등하지 않은 결과를 만드는 충돌을 감지해 트랜잭션을 실패시킬 수 있다. 모든 트랜잭션이 반드시 하나씩 실행되는 방식이 아니다. **전체 트랜잭션 재시도, 충돌률, 행 잠금과의 비용 차이를 실제 동작에 맞게 설명한다.** [PostgreSQL Transaction Isolation](https://www.postgresql.org/docs/18/transaction-iso.html)

### C4. 서명 URL은 일회용이며 객체는 변경할 수 없다는 설명

**원문 위치:** [00:30](https://www.youtube.com/watch?v=soTfFFIQQ8U&t=1800s), [00:40](https://www.youtube.com/watch?v=soTfFFIQQ8U&t=2400s).

S3 presigned URL은 일반적으로 유효 기간 내 재사용할 수 있다. 동일 객체 키에 업로드하면 기존 객체를 대체할 수도 있다. **일회용 토큰이나 불변 객체 버전이 필요하면 별도의 정책과 구현으로 보장한다.** 미디어의 불변 버전 키는 가능한 설계 선택이다. [AWS S3 presigned URL](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html)

### C5. WebSocket에는 L4 로드밸런서가 필수라는 설명

**원문 위치:** [02:07](https://www.youtube.com/watch?v=soTfFFIQQ8U&t=7620s).

AWS Application Load Balancer처럼 L7에서도 WebSocket을 지원하는 제품이 있다. **프로토콜 지원, 연결 시간 제한, 연결 수, 상태 검사와 draining 요구로 선택한다.** [AWS ALB WebSockets](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/load-balancer-listeners.html)

### C6. 영속화 전 성공 ACK와 버퍼 메시지 폐기

**원문 위치:** [02:00](https://www.youtube.com/watch?v=soTfFFIQQ8U&t=7200s), [02:20](https://www.youtube.com/watch?v=soTfFFIQQ8U&t=8400s), [03:08–03:10](https://www.youtube.com/watch?v=soTfFFIQQ8U&t=11280s).

**분석:** 영속화 전에 성공 응답을 보낸 뒤 서버가 중단되거나, 가득 찬 버퍼에서 오래된 메시지를 제거하면 수락한 메시지가 사라질 수 있다. 이는 메시지 유실 방지라는 요구와 충돌한다. 메모리 버퍼만으로는 재시작도 견딜 수 없다.

**보완 지침:** 수락 시점의 내구성 경계를 명시한다. 내구성 있는 기록이 불가능하면 무조건 성공 처리하지 말고 재시도 가능한 실패·backpressure를 적용한다. 로컬 디스크도 디스크/호스트 손실까지 보호하지는 않으므로 목표 실패 범위를 함께 적는다. Kafka의 복제·ACK 보장 역시 설정과 살아남은 복제본에 의존한다. [Kafka producer 설정](https://kafka.apache.org/28/configuration/producer-configs/)

### C7. Redis Pub/Sub를 전달 보장 경로로 해석하기

**원문 위치:** [02:21](https://www.youtube.com/watch?v=soTfFFIQQ8U&t=8460s), [02:26](https://www.youtube.com/watch?v=soTfFFIQQ8U&t=8760s).

Redis Pub/Sub는 at-most-once 전달이며 구독자가 놓친 메시지를 재생하지 않는다. **실시간 알림에 사용하더라도 영속 메시지·전달 상태와 재동기화 경로를 별도로 둔다.** [Redis Pub/Sub 전달 의미](https://redis.io/docs/latest/develop/pubsub/)

### C8. Cassandra 대형 BATCH는 일반적인 100배 고속화라는 설명

**원문 위치:** [02:38–02:41](https://www.youtube.com/watch?v=soTfFFIQQ8U&t=9480s).

Cassandra의 다중 파티션 BATCH는 원자성 보장을 위한 비용을 추가하며 SQL 트랜잭션과 같은 격리 범위를 제공하지 않는다. **대량 수집, 드라이버의 비동기 동시 쓰기, 동일 파티션 배치, 다중 파티션 BATCH를 구분하고 실제 부하에서 검증한다.** [Apache Cassandra BATCH](https://cassandra.apache.org/doc/latest/cassandra/developing/cql/dml.html#batch)

추가로 5초 버퍼 대기는 500ms 전달 목표와 양립하는지 검토해야 한다. 실시간 전달 전에 5초를 기다리는 구조라면 목표를 위반한다. 전달·내구성·후속 저장 경로가 분리되어 있다면 각 경로의 보장을 따로 설명한다.

### C9. Cassandra에 일반적인 primary/read replica 모델 적용하기

**원문 위치:** [02:55–02:57](https://www.youtube.com/watch?v=soTfFFIQQ8U&t=10500s).

Cassandra는 여러 노드가 대등하게 참여하는 분산 구조다. 관계형 DB에서 흔한 단일 primary 쓰기·follower 읽기 도식을 그대로 적용하면 부정확하다. **선택한 저장소의 파티셔닝·복제·일관성 모델을 기준으로 읽기·쓰기를 설명한다.** [Apache Cassandra 기본 아키텍처](https://cassandra.apache.org/_/cassandra-basics.html)

### C10. 공개키로 메시지를 암호화하고 같은 공개키로 복호화한다는 설명

**원문 위치:** [02:42–02:44](https://www.youtube.com/watch?v=soTfFFIQQ8U&t=9720s).

Signal의 X3DH는 공개키·개인키 연산을 통해 공유 비밀을 합의하며, Double Ratchet은 메시지별 키를 파생·갱신한다. 같은 공개키로 누구나 메시지를 복호화할 수 있다는 모델이 아니다. signed prekey와 one-time prekey도 구분해야 한다. **검증된 프로토콜·라이브러리를 사용하고 강의의 단순 설명으로 자체 암호 프로토콜을 만들지 않는다.** [Signal X3DH](https://signal.org/docs/specifications/x3dh/), [Signal Double Ratchet](https://signal.org/docs/specifications/doubleratchet/)

### C11. 종단간 암호화와 서버의 본문 분석을 동시에 가정하기

**원문 위치:** [02:37–02:38](https://www.youtube.com/watch?v=soTfFFIQQ8U&t=9420s), [02:41–02:44](https://www.youtube.com/watch?v=soTfFFIQQ8U&t=9660s).

**분석:** 서버가 평문을 볼 수 없는 E2EE 요구를 적용하면, 앞서 제안한 서버의 본문 기반 멘션 추출·링크 미리보기·검색 색인 생성은 그대로 유지할 수 없다.

**보완 지침:** 본문 분석을 클라이언트로 옮기거나, 명시적으로 허용한 메타데이터만 서버에 제공하는 방식 등으로 신뢰 경계를 다시 설계한다. 미디어·새 기기 등록·키 분배도 동일한 보안 모델과 일치해야 한다. 이 절은 두 설명을 함께 적용할 때 드러나는 요구사항 충돌에 대한 분석이다.

### C12. 한 메시지는 전체 시스템에서 한 번만 쓰인다는 해석

**원문 위치:** [02:28](https://www.youtube.com/watch?v=soTfFFIQQ8U&t=8880s), [02:54–02:55](https://www.youtube.com/watch?v=soTfFFIQQ8U&t=10440s).

**분석:** 본문 한 번 저장과 전체 시스템 한 번 쓰기는 다르다. 같은 강의에서도 오프라인 수신자별 inbox와 사용자별 메시지 복사본을 설명한다.

**보완 지침:** 본문 저장, inbox, 전달 상태, 복제, 사용자별 복사, 재시도 쓰기를 나누어 계산한다. “10억 메시지 = 10억 DB write”처럼 논리량과 물리량을 동일시하지 않는다.

### C13. 중복 방지를 콘텐츠 해시에만 맡기기

**원문 위치:** [02:37](https://www.youtube.com/watch?v=soTfFFIQQ8U&t=9420s).

**분석:** 사용자가 같은 텍스트를 두 번 보내는 것은 정상일 수 있다. 본문이 같다는 이유만으로 두 번째 메시지를 제거하면 데이터가 사라진다.

**보완 지침:** 한 논리 메시지의 재시도에는 같은 안정적인 ID를 사용하고 새 메시지는 새 ID를 사용한다. 파일 중복 저장 방지용 해시와 메시지 요청 중복 제거를 구분한다.

### C14. 장애 복구 시간과 설정 예시를 고정값으로 사용하기

**원문 위치:** [02:36–02:40](https://www.youtube.com/watch?v=soTfFFIQQ8U&t=9360s), [02:45–02:51](https://www.youtube.com/watch?v=soTfFFIQQ8U&t=9900s), [03:09](https://www.youtube.com/watch?v=soTfFFIQQ8U&t=11340s).

**분석:** 배치 크기, 초당 처리량, rate limit, TTL, Kafka 재구축 시간은 환경과 요구사항에 따라 달라진다. 특히 클러스터 전체 복구가 몇 초 안에 끝난다고 보장할 근거는 제시되지 않는다.

**보완 지침:** 숫자는 가정 또는 측정 결과로 표시하고, 복구 시간·손실 허용 범위·버퍼 용량·서비스 거절 조건을 연결한다. 장애 시나리오로 검증되지 않은 복구 시간을 사실처럼 적지 않는다.

## 7. 후속 Skill 명세 제안

이 절은 강의 요약이 아니라 **후속 skill 작성용 설계안**이다. `skill-creator`의 간결한 진입점, 필요한 참고 자료만 읽기, 사용자 범위 보존 원칙을 참고했다.

### 7.1 목적과 적용 조건

**이름 후보:** `design-software-systems`

**설명 후보:** 요구사항과 규모, 기존 시스템 제약을 바탕으로 소프트웨어 시스템을 설계하고, 데이터·API·구성 요소·실패 흐름·트레이드오프를 포함한 설계 문서를 작성하거나 검토한다.

| 적용할 요청 | 적용을 확대하지 않을 요청 |
|---|---|
| 새로운 서비스 또는 주요 기능의 아키텍처 설계 | 단순 함수 구현이나 작은 UI 수정 |
| 기존 서비스의 병목·확장 구조 검토 | “Redis가 무엇인가” 같은 단일 용어 질문 |
| 시스템 설계 면접 연습 | 이미 주어진 그림의 스타일 변경만 요청 |
| 설계안의 정합성·실패 처리 검토 | 별도 요청 없는 실제 인프라 배포·데이터 변경 |

면접 연습은 제한 시간과 대화 진행을 중시하고, 실무 설계는 기존 시스템·운영 비용·이행 경로를 중시한다. 두 목적을 혼동해 실무 요청마다 면접 진행을 시키지 않는다.

### 7.2 입력 계약

| 입력 | 없을 때의 처리 |
|---|---|
| 문제와 기대 산출물 | 사용자 요청에서 우선 추론하고 중대한 모호성만 확인 |
| 핵심 사용자 흐름과 제외 범위 | 초안을 제시하고 가정을 표시 |
| 규모·SLO·보존 기간 | 계산 가능한 가정을 명시하되 사실로 취급하지 않음 |
| 기존 코드·설계·인프라 | 제공되거나 접근 가능하면 먼저 조사 |
| 팀·운영·비용 제약 | 기술 선택에 큰 영향을 주는 부분을 우선 확인 |
| 면접/실무/검토 목적 | 요청의 문맥에 맞춰 진행 방식 조절 |

기존 시스템을 다룰 때는 현재 호출자, 데이터 흐름, API·스키마, 운영 제약을 먼저 파악한다. 코드 근거 없이 기존 구조의 문제나 마이그레이션 가능성을 단정하지 않는다.

### 7.3 실행 규칙 초안

1. **범위를 정한다.** 사실·가정·미해결 질문을 나누고 핵심 사용자 흐름과 제외 범위를 적는다.
2. **위험을 특정한다.** 콘텐츠 전송, 희소 자원 할당, 실시간 전달 중 어느 특성이 중요한지 판단한다. 해당하지 않으면 일반 절차만 사용한다.
3. **계산한다.** 설계 선택에 필요한 부하·저장량·전송량을 단위와 함께 추정한다. 필요 없는 숫자를 늘리지 않는다.
4. **작은 설계를 만든다.** 주요 API·데이터·구성 요소와 대표 읽기·쓰기 흐름을 연결한다. 데이터/API와 구조의 순서는 조절한다.
5. **불변식과 실패를 검토한다.** 원자성, 중복, 동시성, 영속화, 캐시·복제 지연, 복구를 해당 문제에 맞게 다룬다.
6. **확장을 정당화한다.** 추가 구성 요소마다 해결할 병목, 새 비용, 도입 조건을 적는다.
7. **자체 검토한다.** 요구사항과 구조의 충돌, 수치 오류, 근거 없는 기술 단정을 수정한다.
8. **결정을 전달한다.** 선택·대안·대가·미해결 위험·다음 검증을 포함한 문서를 작성한다.

**원문에서 그대로 복제하지 않을 것:** 회사별 사용자 수, 강의 예시의 TTL·배치·rate limit, 특정 DB의 처리량 상한, 모든 시스템의 마이크로서비스화, 매 단계 승인 요청, 실제 운영을 확인하지 않은 성공 주장.

### 7.4 참고 자료 분리 제안

큰 사례와 기술 검증은 필요할 때만 읽도록 분리할 수 있다. 다음은 파일을 실제 생성하기 전의 구조 제안이다.

```text
design-software-systems/
├── SKILL.md
└── references/
    ├── design-workflow.md          # 입력, 계산, 결정 및 산출물 기준
    ├── content-delivery.md         # 대형 파일·CDN·객체 저장소가 중요한 경우
    ├── transactional-inventory.md # 예약·주문·재고 경합이 중요한 경우
    └── realtime-messaging.md      # 연결·전달·기기 동기화가 중요한 경우
```

본 문서 6절의 보완 사항은 해당 참고 자료에 함께 배치한다. `SKILL.md`에는 핵심 절차와 참고 자료를 읽을 조건만 남긴다. 규모 추정 스크립트 등은 실제 반복 작업의 이점이 확인될 때 추가하며 처음부터 빈 디렉터리나 불필요한 도구 의존성을 만들지 않는다.

## 8. 설계 산출물 템플릿

다음은 실무 설계 문서용 예시다. 작은 요청에서는 필요한 항목만 사용한다.

```markdown
# [시스템명] 설계

## 목적과 범위
- 핵심 사용자 흐름, 포함·제외 범위
- 확인된 사실, 가정, 미해결 질문

## 요구사항과 불변식
- 기능, 규모, 연산별 SLO, 보존·정합성·운영 제약
- 절대로 깨지면 안 되는 업무 조건

## 용량 추정
- 입력값과 단위, 계산식, 평균·피크, 제외한 비용

## 데이터와 외부 계약
- 엔터티, 접근 패턴, 키·인덱스, 상태 전이
- API/이벤트 요청·응답·오류·멱등성

## 구조와 주요 흐름
- 구성 요소별 책임, 원본 저장소, 동기·비동기 경계
- 읽기·쓰기·실패·복구 흐름

## 확장과 운영
- 예상 병목, 개선 순서, 도입 조건, 새 운영 비용
- 관측 지표, 데이터 보존, 장애 조치, 배포·되돌림

## 결정과 검증
- 선택·대안·근거·대가·재검토 조건
- 확인한 근거와 아직 필요한 실험
- 미해결 위험
```

설계 문서에는 독자가 각 결정을 검토할 수 있는 근거가 있어야 한다. 구성 요소 목록과 다이어그램만 있거나, 모든 실패를 “재시도” 하나로 처리하면 완료로 보지 않는다.

## 9. Skill 검증 시나리오

아래는 **skill 완성 후 실행할 평가 계획**이다. 이번 문서 작성 과정에서 실제 서비스 테스트나 skill 실행 평가를 수행한 것은 아니다. 문구·제목 일치보다 의사결정과 보장 조건을 평가한다.

| 시나리오 | 기대되는 판단 | 실패 판정 예시 |
|---|---|---|
| 소규모 음악 서비스 설계 | 미디어와 메타데이터 경로를 구분하고 규모에 맞는 구조 제시 | 이유 없이 다중 리전·샤드·Kafka를 모두 도입 |
| 음악 사용자 수가 100배 증가 | 전송량·API 부하·메타데이터 부하를 재계산하고 단계적 확장 | 곡 개수만 보고 DB 샤딩 확정 |
| 마지막 객실을 두 사용자가 동시에 예약 | 확인과 차감의 원자성 및 모든 숙박일의 성공/롤백 보장 | 먼저 조회 후 별도 INSERT만 제시 |
| 같은 예약 요청의 재전송 | 동일 결과 반환, 서버 멱등성, 키 충돌 처리 | 프런트엔드 버튼 비활성화만 제시 |
| 결제 성공 후 내부 확정 처리 실패 | 중간 상태, 결과 대조, 재처리·보상 제시 | 무조건 새 결제를 재시도 |
| 검색 색인 반영 지연 | 오래된 검색 결과를 허용해도 확정은 원본 재고에서 검증 | 검색 결과를 근거로 바로 예약 확정 |
| ACK 직후 채팅 서버 종료 | 수락한 메시지가 복구 가능한 저장소에 존재 | 메모리에만 저장하고 `sent` 처리 |
| Redis 장애 또는 Pub/Sub 구독 단절 | 영속 기록에서 미전달 메시지 복구·재동기화 | Pub/Sub 자체가 재전달한다고 가정 |
| 그룹 100명·각 사용자 3개 기기 | 수신 대상·전달 상태와 fanout 비용을 계산 | 전체 시스템 쓰기와 전송이 한 번이라고 주장 |
| 늦게 재접속한 두 번째 기기 | 기기별 동기화 위치, 보존 만료, 중복 제거 정의 | 한 기기 ACK 직후 모든 서버 사본 삭제 |
| E2EE와 서버 본문 검색을 동시에 요구 | 신뢰 경계 충돌을 설명하고 가능한 변경안 제시 | 서버가 암호문에서 평문을 자유롭게 분석 |
| 500ms 목표와 5초 저장 배치 | 전달·수락·후속 저장 경로의 지연과 내구성을 분리 검토 | 서로 모순되는 목표를 그대로 유지 |
| 기존 시스템에 기능 추가 | 호출자·API·스키마 영향 확인 후 최소 변경 설계 | 근거 없이 전체 마이크로서비스 전환 |

### 완료 기준

- [ ] 요구사항마다 담당 구성 요소와 검증 방법이 연결된다.
- [ ] 불변식과 이를 지키는 저장소 연산·트랜잭션 경계가 명확하다.
- [ ] 주요 계산에 입력값·단위·피크·보존·복제 등의 가정이 있다.
- [ ] 성공 응답이 보장하는 상태와 장애 후 복구 범위가 일치한다.
- [ ] 주요 선택에 대안·대가·재검토 조건이 있다.
- [ ] 요구와 무관한 기술·인프라·권한 확대가 없다.
- [ ] 강의 예시, 문서의 보완 설계, 실제 확인 사실이 구분된다.
- [ ] 기술 세부 주장은 사용 중인 제품·버전의 공식 문서와 일치한다.

수락한 데이터 유실, 허용하지 않은 중복 재고 할당, 권한 우회, 암호화 요구 위반은 다른 항목이 잘 작성되어 있어도 통과로 판정하지 않는다.

### 기술 검증 자료

본문 6절의 각 보완 사항에 PostgreSQL, AWS, Redis, Apache Cassandra, Apache Kafka, Signal의 공식 문서를 직접 연결했다. 제3자의 영상 자동 요약을 기술 판단의 근거로 사용하지 않았다.

후속 skill에서는 강의 링크를 배경 출처로 유지하고, 실제 실행 규칙은 검증된 절차로 작성한다. 특정 제품을 선택하는 작업에서는 해당 버전의 공식 문서를 다시 확인한다. 암호화·일관성·전달 보장처럼 중요한 속성은 구현과 설정에 따라 달라지므로 이 문서의 사례만으로 보장을 선언하지 않는다.

이 문서의 후속 작업은 skill 본문과 선택형 참고 자료를 작성하고, 9절의 대표 시나리오로 행동을 검증하는 것이다. 원본 자막 전체를 skill에 넣기보다, 반복적으로 의사결정을 개선하는 규칙과 필요한 사례를 추려 넣는다.
